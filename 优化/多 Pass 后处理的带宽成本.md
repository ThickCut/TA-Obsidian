# 多 Pass 后处理的带宽成本

> [!abstract] 一句话
> 多 pass = 把画面反复"渲染到纹理 → 再处理 → 再渲染"。**每一次 pass 都是一次全屏数据的进出显存**，在 [[TBR 与 IMR 渲染架构|TBR 移动端]]每一步都是钱。

---

## 一、什么是 Pass / 多 Pass

**Pass（渲染通道）**：GPU 完整地跑一遍渲染流程。

- **单 pass**：直接画到屏幕，一次搞定。
- **多 pass**：先画到一张**中间纹理（RT，Render Target）**，再对这张纹理做处理，可能再画到下一张纹理……最后才输出到屏幕。

> [!note] 典型例子
> 后处理链条：**模糊 → 泛光（Bloom）→ 色调映射 → 抗锯齿**，可能一个效果一个 pass，一帧就跑好几个全屏 pass。

---

## 二、为什么多 pass 贵

每次 pass 都意味着：

1. **全屏读**：把上一张 RT 读进来。
2. **全屏写**：把结果写到下一张 RT。

而"全屏读 + 全屏写"就是**带宽开销**。桌面端带宽充足，随便跑；**移动端带宽稀缺，多一个 pass 就多一笔显存的进出账**。

> [!warning] 关键
> 移动端多 pass 的成本**主要是带宽，不是算力**。
> 一个 1080p 的 RT，读写一次就是几百万像素 × 每像素几个字节，再乘上几个 pass，带宽直接吃满。

---

## 三、为什么 TBR 下更痛

回到 [[TBR 与 IMR 渲染架构]]：

- TBR 的本意是"画面在片上内存里处理完，一次性写回显存"。
- 但**多 pass 会强制"把结果从片上内存吐回显存，再读回来"**，破坏了 TBR 省带宽的优势。
- 所以移动端要**尽量让渲染在一个 pass 内完成**，别反复进出。

---

## 四、移动端的应对

| 策略 | 做法 |
|---|---|
| **合并 pass** | 把多个后处理效果合成一个 shader，一次算完 |
| **降分辨率** | 后处理用**半分辨率**（甚至 1/4）的 RT，模糊类效果肉眼难分辨，带宽直接砍一截 |
| **用 Compute** | 某些效果用 compute shader 做，避免走完整的渲染管线 |
| **避免 ping-pong** | 别在 A、B 两张 RT 之间来回反复拷（比如多级模糊），能单张就地处理就单张 |
| **延迟到必要才做** | 后处理能关就关、能合并就合并 |

> [!tip] 记忆点
> - 多一个 pass = 多一次全屏显存进出。
> - 移动端最省的做法：**少 pass、低分辨率、合并计算**。
